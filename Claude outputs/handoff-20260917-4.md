## Decisioni e conclusioni
- **Forma scelta**: un giorno alla volta, come iOS. Striscia della settimana in alto + timeline oraria del giorno selezionato. Il mese resta solo come etichetta di navigazione.
- **Progressi mensili eliminati**: heatmap, popup del giorno, "Prossimi impegni (14 gg)" e il CSS `ANALYTICS`/`hm-*`/`dp-*`/`evento-*`/`prossimi-*` sono stati rimossi. Sopravvive solo il colore: il cerchio col numero del giorno nella striscia è tinto con `heatColor(calcPct(ds))`, come l'utente ha chiesto ("ogni giorno si deve colorare con la quantità dei progressi fatti quel giorno").
- **Sezioni spostate in Pianifica**: "Impegni ricorrenti" (con la rotellina) e "Abitudini settimanali" ora stanno in fondo a `#screen-plan`, agganciate a `renderPlan()`. Il Calendario contiene solo il calendario.
- **Modello eventi esteso**: `{ id, titolo, tipo: 'impegno'|'scadenza', tuttoIlGiorno, ora: 'HH:MM', durata: minuti, completato }`. `normalizeEvento()` migra i vecchi eventi (senza `durata` → 60 min; senza `ora` o malformata → `tuttoIlGiorno`); `ensureEventi()` è chiamata da `ensureSlotArrays()`, quindi ogni giorno letto con `getDay()` è normalizzato.
- **Bug risolto (era serio)**: gli eventi non venivano mai salvati su Supabase e un load dal cloud li **cancellava**. Ora `sbSaveDay()` invia `eventi`, i tre loader lo rileggono, e il nuovo `adoptRemoteDay()` impedisce che una riga remota senza eventi sovrascriva quelli locali. Se la colonna manca, al primo errore il flag `eventiColumnOk` va a `false`, il salvataggio riprova senza `eventi` e la app continua a funzionare (eventi solo in localStorage).
- **SQL che l'utente deve ancora eseguire su Supabase**: `alter table public.days add column if not exists eventi jsonb not null default '[]'::jsonb;`
- **Effetto collaterale voluto**: `sbSaveDay()` ora controlla `error` del risultato Supabase invece di affidarsi solo al try/catch (prima un errore API passava per "sincronizzato").
- **Swipe e carosello**: `.cal-scroll` ha `touch-action: pan-y`, così un trascinamento orizzontale dentro la timeline non muove il carosello tra schermate e viene gestito a mano (± 1 giorno; sulla striscia ± 1 settimana).
- **Metodo di lavoro**: i subagent `dayflow-builder` / `dayflow-implementer` / `dayflow-verifier` definiti in `.claude/agents/` **non sono disponibili in questa sessione Cowork** (ambiente diverso da Claude Code sulla macchina); il lavoro è stato fatto direttamente, con verifica tramite test automatizzati.
- **Git**: dal terminale Linux di questa sessione `git` funziona ma vede tutto il working tree come modificato (il repo è checkout CRLF su Windows, l'indice LF). Commit e push li fa l'utente dal suo terminale, come prima.
- **Attenzione CRLF**: `dayflow1_0.html` è memorizzato **con CRLF**, `CLAUDE.md` con **LF**. Qualsiasi script Python che riscrive questi file deve preservare i fine riga, altrimenti il diff esplode a file intero.
