# Handoff: DayFlow, split meccanico del file unico (passi 0 e 1)

## Contesto
DayFlow è un habit tracker personale (PWA su GitHub Pages, installata su iPhone da Safari, UI in italiano). È usata solo dall'autore. Oggi l'intera app vive in `dayflow1_0.html` (~298 KB: ~3800 righe CSS, ~280 HTML, ~3100 JS, 224 funzioni top-level, 80 handler inline `onclick=` ecc.). Leggi `CLAUDE.md` nella root prima di toccare qualsiasi cosa: descrive architettura, stato globale `S`, logica di sync con Supabase e la tabella delle funzioni per categoria.

## Obiettivo di questo handoff
Solo due passi, entrambi meccanici: sistemare il service worker e dividere il file unico in più file classici (CSS + script con `defer`). **Nessuna riga di logica JavaScript deve cambiare**: si copia e si sposta, non si riscrive. La conversione a ES modules e i test verranno fatti in una sessione successiva da un altro agente: non farli.

## Decisioni già prese (non rimetterle in discussione)
- Niente framework, niente bundler, niente Vite. Script classici con `defer`, tutto resta globale.
- Gli 80 handler inline (`onclick=`, `oninput=`, `onchange=`, `onkeydown=`) restano invariati.
- La logica di sync (tutto ciò che riguarda Supabase, `scheduleSync`, `syncPendingDays`, `flushAllSync`, `adoptRemoteDay`, coda persistita, retry) va spostata in blocco in un solo file, senza modifiche.
- `index.html` diventa la pagina vera; `dayflow1_0.html` resta come meta refresh verso `index.html` così la PWA già installata su iPhone continua ad aprirsi. Oggi è il contrario.
- Lavorare sul branch `refactor/split`, un commit per passo.
- Il rischio da evitare è la regressione: cose che funzionavano e smettono di funzionare. Verifica manuale in browser obbligatoria dopo ogni passo.
